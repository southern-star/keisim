# 360° のリグ（後ろ向きの広角カメラ）の設計書

KeiPilot Mc の前向きの 2 台（広角 180° と望遠 50°）に、後ろ向きの 180° の円筒カメラを 1 台足して、水平 360° を見せる計画です。2026-11-28 に、開発のできないノート PC で議論して書きました。**まだ何も実装していません。** 実装と学習は RTX 3060 の PC で行います。

- 新しいリグの名前は `wide_narrow_rear` です。カメラは `wide`、`narrow`、`rear` の順です。
- 段階は S0〜S5 で、関門は G0〜G4 です。**G0 と G1 では、絵と数字を見せて止まります。** GPU を長く使う S3 は、G1 を通ってから始めます。
- 新しい選択肢は、すべて既定でオフです。今までのリグ（`front`、`wide_narrow`）の街・エピソード・画像・ラベルは、ビット単位で変えません。

読む順番: [roadmap.md](roadmap.md)（とくに「決めたこと」と「KeiPilot Mc の弱点」）、[multicam.md](multicam.md)（2 章の作りと、3 章の 8 回目の教訓）、この文書。

## 1. なぜ後ろを見るか

### 1.1 今のカメラでは見えないもの

roadmap と multicam.md の 5 章に、後ろが見えないための弱点が 2 つあります。

- **横や後ろからの割り込み**: 「2 台とも前向きなので、真横より後ろは見えません」。
- **左後ろから来る自転車の巻き込み**: roadmap の「決めたこと」で、「見えない巻き込みは、後ろのカメラと同じく、当面は受け入れます」としています。

### 1.2 エキスパートとカメラの食い違い

multicam.md の 8 回目の教訓は、「ラベルがカメラの見えないものに従うと、避けることを覚えます」でした。今のエキスパートには、後ろについて 2 通りの扱いが混ざっています。

| 場面 | エキスパートが使う情報 | 今のカメラ | コード |
|---|---|---|---|
| 自転車の巻き込み確認（`expert_bike_visible`） | 先頭のカメラに映る自転車だけ。後ろから追い付く見えない自転車は、全部の判断から外す（`behind_unseen`） | 合っている | `keisim/expert.py` の `bikes_seen`、`bike_scan`（`behind_unseen`） |
| 自車の車線変更 | 移る先の車線の**後ろの車**も含めて隙間を見る（`change_room` の `dx` は負も見る） | **食い違っている** | `keisim/route.py` の `change_room`、`keisim/expert.py` |
| 譲り（`expert_yield_visible`） | 先頭のカメラに映る車だけ | 合っている | `keisim/expert.py` の `tables()`（830 行目あたり） |

後ろが映れば、巻き込み確認の縛りを外せます。車線変更のラベルとカメラの食い違いもなくなります。どちらも、観測とラベルの食い違いが減る方向の変更です。

### 1.3 先に確かめること

Mc を作ったときは、札幌の止まれ 255 か所で「横の優先道路の 30 m 先が映るか」を測ってから、カメラを決めました（multicam.md の 1 章、`tools/sightline.py`）。今回も同じ順にします。後ろを見ないと正しく運転できない場面がどれだけあるかを、GPU を使う前に数えます（S1、関門 G1）。**場面が少なければ、後ろのカメラを足しても数字に出ません。そのときは G1 で止めます。**

## 2. リグの形

### 2.1 カメラ

```python
# keisim/config.py の CAMERA_RIGS に足す（web/src/rig.js の RIGS にも同じものを足す）
"wide_narrow_rear": (CameraConfig(name="wide", projection="cylindrical", fov_deg=180.0),
                     CameraConfig(name="narrow", fov_deg=50.0, pitch_deg=2.0),
                     CameraConfig(name="rear", projection="cylindrical", fov_deg=180.0, yaw_deg=180.0)),
```

- **並びは wide、narrow、rear です。** `wide` と `narrow` は `wide_narrow` と同じ設定で、同じ位置に置きます。先頭のカメラを使う所（`env.cfg.camera`、KeiView の `_actors` と空と影、`bikes_seen`）と、mc14 の位置の埋め込み（`pos3[0]`、`pos3[1]`）が、今のまま使えます。後ろの画像はシャードの `jpg_c2` と `seg_c2` に入ります。
- **後ろのカメラは、広角と同じ点（前に 0.6 m、高さ 1.55 m）に置き、180° 回します。** 2 台の 180° の円筒で、すき間のない 360° になります。
  - 後ろのカメラを車の後ろ（x = −1.4 m あたり）に置くと、車の横に長さ約 2 m の帯ができ、どちらのカメラにも映りません。車の横 1 m を走る自転車は、追い越すあいだ消えます。巻き込みを見るためのカメラなので、この帯は困ります。
  - シミュレーターは自車の車体を描かないので、同じ点に置けます（S0 で確かめる。2.3）。実車なら、屋根の上の 360° のカメラポッドにあたります。
- 後ろのカメラの `pitch_deg` は、広角と同じ既定の 8° です。円筒の作り（`keisim/render/rig.py` の `cylinder_faces`）は `yaw_deg` に対応しているので（98 行目）、新しい射影は要りません。

### 2.2 重さ（見積もり。S0 で測る）

| | `wide_narrow`（今） | `wide_narrow_rear` |
|---|---:|---:|
| デコーダーが読むトークン | 500 | 750 |
| 幹（ResNet18）の計算 | 2 台ぶん | 3 台ぶん（1.5 倍） |
| KeiSim の描画（1 フレーム） | 約 28 ms（multicam.md の 2 章） | 約 50 ms（面が 4 枚から 7 枚に） |
| KeiView の描画（RTX 3060、RGB とラベル） | 66 ms（recon_view.md） | 約 110 ms |
| 学習データ（1 フレーム） | 約 25 KB（28.8 GB / 116 万） | 約 37 KB |
| ブラウザの推論（RTX 3060、描画を止めて） | WebGPU 25〜28 ms、WASM 約 400 ms | WebGPU 約 40 ms、WASM 約 600 ms |

8 台構成（Tesla 型）は採りません。トークンが 2000 になり、RTX 3060 での学習もブラウザも持ちません。

### 2.3 直す必要がある所（コードを読んで見つけたもの）

後ろのカメラを足しただけでは、次の 4 か所が「前しか見えない」前提のまま残ります。どれも新しいリグのときだけ動きを変え、今までのリグでは変えません。

1. **KeiView の影の範囲**（`web/vendor/sakuragaoka/core/sky.js` の `update`、`web/src/ego.js` の 256 行目と 281 行目）。
   - 影の箱は一辺 2S で、先頭のカメラの 0.45 S 前に置かれます。S は品質で決まります（`web/src/main.js`。収集の既定の `keiview_quality = "medium"` は 60 m、`high` は 75 m）。medium では、前は約 87 m まで影がありますが、**後ろは約 33 m で影が切れます**。
   - 影の地図は、最初の 1 枚（`shadows: i === 0`）を描くときだけ作られます。
   - 直し方: 前の面を今のとおり描いてから、影の箱を後ろ向きに置き直し、後ろの最初の面で影の地図を作り直します。前の画像は今とビット単位で同じままです（関門 G0）。影の地図を 1 回多く描くぶん重くなるので、S0 で測ります。
2. **渋滞ほぐしの瞬間移動**（`keisim/traffic.py` の 2017 行目あたり、`keisim/bicycles.py` の 1165 行目あたり）。
   - 止まったままの NPC と自転車は、自車の向きから 60°（`TrafficConfig.view_half_deg`）より外にいれば、カメラに見えないものとして移されます。NPC は `release_hidden` のとき（`jam_fixes` のスイートでは有効）、自転車はいつもです。
   - 後ろのカメラには、移される瞬間が映ります。
   - 直し方: 新しいリグでは、リグのどのカメラにも見えないとき（`visible_from` の和。建物の陰も入る）か、`view_dist` より遠いときだけ移します（新しい選択肢 `TrafficConfig.release_view = "heading" | "rig"`、既定は `heading`）。
   - 今の広角 180° でも、60°〜90° の横にいる車は映ったまま移されえます。今のリグの動きは変えませんが、S1 で件数を数えて記録します。
3. **エキスパートの「見えるか」**（`keisim/expert.py` の `bikes_seen`、`riders_seen`、`tables()`）。
   - 今は `env.cfg.camera`（先頭の 1 台）の向きと画角だけを見ていて、カメラの `yaw_deg` も見ていません。
   - 直し方: リグの全部のカメラについて、カメラごとの位置と向き（自車の向き + `yaw_deg`）で `visible_from` を呼び、和をとる関数を 1 つ作り（例: `Expert.rig_visible`）、この 3 か所から使います。
   - `wide_narrow` では、望遠は広角の画角の内側にあり、`max_dist` も同じなので、和は今の先頭のカメラと同じ結果になるはずです。念のためハッシュで確かめます（G0）。
4. **自車の車体**: KeiSim も KeiView も、モデルのカメラの画像に自車を描かないはずです。後ろ向きのカメラは自車の真上から後ろを見るので、もし描かれていれば屋根と後ろのガラスが映ります。KeiView の pilot モード（`web/src/pilot.js`）は、主画面には自車を描きます。モデルの画像からは外れていることを、S0 で絵で確かめます。

## 3. 学習データとモデル

### 3.1 今までのデータ（後ろの画像がない）をどうするか

今の学習は、すべてのシャードが同じリグであることを求めます（`scripts/train.py` の 191〜198 行目、`keipilot/data.py` の 318〜320 行目）。今までの 116 万フレームには後ろの画像がありません。

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| **A（おすすめ）: 欠けたカメラを伏せて混ぜる** | 後ろのないフレームでは、後ろの 250 トークンをデコーダーの `memory_key_padding_mask` で伏せ、後ろのセグメンテーションの損失も外す | 今までのデータを全部使える。同じ重みで「後ろを伏せた」走りを測れるので、後ろのカメラの効き目を対照なしで見られる | モデル・データ・学習に手が入る |
| B: 全部集め直す | 3 台のリグで、今までの回の場面を全部集め直す | コードが単純 | DAgger は前の回のモデルが運転するので、同じエピソードは再現できない。集め直しに数日かかる |

案 A で、後ろのないフレームのラベルは、後ろを見ないエキスパート（今の `expert_bike_visible`）が付けたものです。入力（後ろなし）とラベル（後ろを見ない）が合っているので、8 回目の教訓に反しません。車線変更のラベルだけは、今までどおり後ろを見たエキスパートのものです（1.2）。

### 3.2 モデルの変更（`keipilot/model.py`）

- `load_compatible`: 今は 1 台のチェックポイントから全カメラに位置の埋め込みをコピーするだけです。2 台から 3 台へは、`pos3[0:2]` と `pos4[0:2]` をそのまま使い、後ろの `pos3[2]` と `pos4[2]` は広角（`[0]`）からコピーします（同じ円筒の射影なので）。
- `forward(..., cam_valid=None)`: `cam_valid`（B, n_cams）が偽のカメラのトークンを、`self.decoder(q, mem, memory_key_padding_mask=...)` で伏せます。`None` のときは今と同じ計算にし、ONNX の書き出しも今のまま（伏せる入力なし）にします。
- 安全層（`keipilot/agent.py` の BrakeHold、RedHold、YieldHold）は変えません。
- `agent.py`: チェックポイントのリグがデータのリグの先頭部分なら（mc14 の `wide_narrow` と `wide_narrow_rear`）、先頭の K 台だけをモデルに渡します。mc14 が 3 台のリグの街を運転して、後ろの画像も記録する DAgger に使います（S3）。

### 3.3 データと学習（`keipilot/data.py`、`scripts/train.py`）

- `train.py --mix_rigs 1`: `wide_narrow` と `wide_narrow_rear` のシャードを一緒に読みます。`n_cams` は多いほう（3）にします。後ろのないフレームは、後ろの画像を 0、`cam_valid` を偽にします。
- 後ろのないフレームでも幹は 3 台ぶん回ります（無駄ですが単純です）。遅すぎるときだけ、後ろのないフレームの幹を飛ばす作りにします。
- 新しいフレームの後ろを、確率 p で伏せる拡張（`--rear_drop`、既定 0）も入れておきます。使うかどうかは S3 の試しで決めます。

## 4. 後ろが効く場面と、その測り方

### 4.1 新しい指標

NPC は IDM で前の車（自車も含む）に合わせて減速するので、後ろを見ずに車線を変えても、ほとんど衝突になりません。**衝突の数だけでは、後ろのカメラの効き目が見えません。** `scripts/evaluate.py` に、次の数を足します。

| 指標 | 中身（しきい値は S1 で決める） |
|---|---|
| 後ろの車に強いたブレーキ | 自車が前に入った NPC が、自車のために `idm_b`（3 m/s²）を超えて減速した回数 |
| 割り込みの近さ | 自車が隣の車線に入った瞬間の、後ろの車との車間と TTC（最小値と、しきい値を下回った回数） |
| 巻き込み | 自車の左折で、左後ろから来た自転車（車道と歩道）が止まった、または強く減速した回数。接触はもちろん数える |

### 4.2 シミュレーターに足す動き（どれも既定はオフ）

| 選択肢（案） | 中身 | ねらう場面 |
|---|---|---|
| `TrafficConfig.speed_spread` | NPC の望む速度を、制限速度の 0.9〜1.2 倍でばらつかせる。後ろから速い車が追い付いてくる | 片側 2 車線の車線変更、ランプ |
| `TrafficConfig.npc_cut_in` | 隣の車線の NPC が、自車のすぐ前に車線を変えてくる（今の NPC の車線変更は `change_room` で自車にも隙間を残すので、それより短い隙間で入る） | 横からの割り込み |
| `TrafficConfig.bike_behind` | 左折の手前で、自車の左後ろ 15〜30 m に、自車より速い自転車を出す | 巻き込み |
| `evaluate.py --via_left`（`via_right` と同じ作り） | 左折を通るルートだけを選ぶ | 巻き込み |

### 4.3 新しい評価スイート（案）

| スイート | 街 | 中身 |
|---|---|---|
| `rear_lc` | `suburban` と `ramps` | `speed_spread` あり。車線変更とランプへの分流を含むルート |
| `cut_in` | `suburban` | `npc_cut_in` あり |
| `left_hook` | `crosswalks_bk8` と同じ街 | `--via_left`、`bike_behind`、`sidewalk_bikes`。corner-fix ブランチの `bike_ego_sides` が main に入っていれば、それも使う |

どれも、エキスパートを 3 通りで走らせます。

- 全部を知るエキスパート（今の車線変更と同じ）。
- `wide_narrow` に見えるものだけを使うエキスパート。
- `wide_narrow_rear` に見えるものだけを使うエキスパート。

**2 番目が 3 番目より目に見えて悪いこと**が、後ろのカメラに意味のある条件です（関門 G1）。

### S0: リグと描画（関門 G0、絵と数字を見せて止まる）

やること:

- `keisim/config.py` と `web/src/rig.js` に `wide_narrow_rear` を足す（2.1）。
- KeiView: 影の箱の置き直し（2.3 の 1）。KeiSim: 円筒が `yaw_deg = 180` で正しく描けるかの確認。
- `Expert.rig_visible` と、`TrafficConfig.release_view`（2.3 の 2 と 3）。
- 自車の車体が映らないことの確認（2.3 の 4）。

G0 で見せるもの:

1. **今までのリグが変わらないこと**: `wide_narrow` と `front` で集めた npz の sha1、`tools/keiview_hash.py`、`web/tools/golden.mjs`（ピクセル単位）、mc14 の評価の数本（同じ結果）。
2. **新しいリグの前の 2 枚が、`wide_narrow` の 2 枚とビット単位で同じこと**（KeiSim と KeiView の両方）。案 A（3.1）では、今までのデータと新しいデータの前の画像が同じ分布であることが前提になります。
3. **後ろの絵**: KeiSim と KeiView で、格子の町、札幌、片側 2 車線の街、大きな交差点の街から数場面ずつ。空の継ぎ目、影の切れ目、自車が映っていないこと、前と後ろの継ぎ目（真横）に物が欠けていないこと。
4. **速さ**: KeiSim と KeiView（RTX 3060）の 1 フレームの描画時間（2.2 の表の実測）。

### S1: 後ろが要るかを数える（関門 G1、続けるかどうかを決めて止まる）

やること:

1. **今のスイートでの数え上げ**: KeiSim の 740 ルートと、自転車の 3 スイート（`_bk8`）をエキスパートで走らせます。各フレームで、エキスパートの判断（譲り、巻き込み、車線変更の隙間）に関わる相手のうち、`wide_narrow` には見えず `wide_narrow_rear` には見えるものがあるフレームの割合と、場面の種類を数えます。`tools/sightline.py` の数え方を参考にします。
2. **渋滞ほぐしの瞬間移動の件数**（2.3 の 2）。今のリグで、広角に映ったまま移された件数も数えます。
3. 4.1 の指標、4.2 の動き、4.3 のスイートを足し、エキスパートの 3 通りと、mc14（後ろなし）の値を測ります。

G1 の判定:

- 4.3 のスイートで、`wide_narrow` に見えるものだけのエキスパートが、`wide_narrow_rear` のエキスパートより、4.1 の指標で目に見えて悪いこと（数字の線は S1 の結果を見て、学習の前に決めて書く）。
- 1 の割合も見せます。割合が小さく、新しいスイートでしか差が出ないなら、「後ろのカメラは、作った場面でしか効かない」ことになります。続けるかはユーザーが決めます。

### S2: モデル・データ・学習の変更（関門 G2）

3 章の変更を入れ、小さなデータ（数万フレーム）で試します。

G2:

- `cam_valid=None` と、全部のカメラが有効なときの出力が、変更の前と同じ（mc14 を 2 台のリグで読んだときのビット単位の一致。KeiReality の Phase 0 と同じ確かめ方）。
- 3 台のモデルを mc14 から読み、後ろを伏せたときの出力が mc14 と同じ（`load_compatible` の確認）。
- 混ぜた学習が、1 エポック分ほど問題なく回る。

## 6. 守ること

- **既定はオフ**: 新しい選択肢はすべて既定でオフにします。`wide_narrow` と `front` の街・エピソード・画像・ラベル・評価の結果は、main とビット単位で同じままにします（roadmap の「決めたこと」）。
- **前の 2 枚は同じ**: 新しいリグの前の 2 枚は、`wide_narrow` とビット単位で同じにします。影の箱を動かして前の画像を変える直し方は採りません。
- **見えないものに従わない**: 新しいリグのエキスパートは、リグに見えるものだけで判断します（車線変更の隙間も含む）。全部を知るエキスパートは、比べるためだけに使います。
- **KeiReality との関係**: `experiment/keireality` ブランチは mc14 の特徴（500 トークン）を使い、`keipilot/model.py` と `keipilot/agent.py` に手を入れています。この計画は main から進め、KeiReality は mc14 のまま触りません。マージのときに、この 2 つのファイルがぶつかります。
